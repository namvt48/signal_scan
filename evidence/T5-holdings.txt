CONTRACT NOTES
  WalletTokenHolding { ca: string; amount: number } — amount in TOKEN units (raw / 10^decimals,
  integer part never loses digits: bigint split, float only for the fraction).
  A tracked CA the wallet does not hold → amount 0, NEVER dropped (the writer needs the 0 to
  delete the stale row). Unknown decimals + balance>0 → token skipped + WARN, never a guessed
  scale. Reverted sub-call (allowFailure=true) → amount 0. Malformed aggregate3 hex → throws,
  never a silent empty list. Sol path untouched — byte-identical behavior, proven by the
  existing sol tests (mint-filtered per-pair calls, sweep cost, RPC failure rejects) passing
  unmodified.

ADJACENT FIX (pre-existing flake caught by this task's acceptance runs — NOT T5 code)
  test/ratelimit/integration.test.ts flaked ~1 run in 8 ("window at ... had 6") under
  full-suite parallel load. Root cause: the Limiter stamped window/min-interval slots with
  the drain-loop decision time while the test measured fn-entry Date.now() — both ms-granular
  reads inside one synchronous tick, so a boundary admission (6th job stamped exactly at
  ts0+1000) plus a 1ms anchor drift yielded 6 test-measured starts in a 1000ms probe window.
  Fix 1 (product, src/ratelimit/limiter.ts): start() re-reads clock.now() at DISPATCH time
  instead of reusing the scheduling-time value — slot accounting matches actual request time.
  Fix 2 (test): probe window right edge t+999 instead of t+1000 — 1ms tolerance for the
  irreducible ms-clock drift; any real composition bug over-admits by >=5ms and still trips.
  Verification: 10/10 standalone runs PASS (was ~12% flake rate), full suite 306/306, tsc exit 0.
