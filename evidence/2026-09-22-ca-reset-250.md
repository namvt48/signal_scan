## Two follow-up questions answered (2026-09-22T17:12–17:14Z)

### 1. LEEROY `5TPNaSi63H…` has `trackedBy` but `trackedInflow` = 0 — not a bug, a cut-over artifact

`wallet_trades` for that CA = **0 rows**; `wallet_token_state` = 1 row (`FfztZq1out…` = "Deployer/ Snip1",
26,954,931 token units, $4679.6). So the name in `Tracked by` comes from the **holding** half of
`trackedByNames` (`token_amount > 0`), not from a trade; `trackedInflow` = `sumTrackedBuyUsd` =
Σ `amount_usd WHERE side='buy' AND ts >= now-24h AND source='watch'` → no rows → 0.

Timing proof: the event that created the CA is in `events.jsonl` (`BUY`, `FfztZq1out…`, label `09-23 00:04:08`
= UTC+7 → **17:04:08Z**) and `tracked_cas.added_at` = **17:04:28Z** — 20 s later, i.e. **2 m 37 s BEFORE the
19:07:05 CEST (17:07:05Z) deploy**. The old build could post CAs but not trades, so that buy left no row.
BRRR's buy landed at **17:07:32Z**, 27 s *after* the deploy → row exists → inflow 5358.11. There is no
backfill: the column fills on the next BUY detected by the new build inside the 24 h window. (The CA post
does carry the USD — `tracked_cas.entry_usd = 1348.98` — but inflow never reads `entry_usd`.)

### 2. Setup shows only `fresh` — `t100`/`lf` have no producer except the 12 h setup sweep

Payload is `nansen: {score, pass:{fresh,t100,lf}, fresh}`; `t100` reads `token_state.t100_multiple`, `lf`
reads `token_state.genesis_bal`. Across the whole fresh DB (12 `token_state` rows):
`nansen_fresh_pct` 12/12, `nansen_t100_pct` 12/12, **`t100_multiple` 0/12, `genesis_bal` 0/12,
`anchor_at` 0/12** → no CA has them, so it is systemic, not per-CA.

- Only `refreshSeries` (`poller.ts:282`) computes those four, and its sole caller is `setupSweep`
  (`poller.ts:230`, scheduled `poller.ts:552`) — one paced pass over the queue every `config.pollSetupMs`,
  which on 250 is unset → default `43_200_000` = **12 h**. It ran once at startup with an empty queue
  (`[poller] setupSweep done in 1ms`) and has not run since.
- `kickNansen` — the frequent path, 14 calls in 20 min — deliberately **passes t100/lf through unchanged**
  (`passThroughAnalytics`, `poller.ts:214`), so it can never fill them.
- The series the pass needs is also failing intermittently on the browser door:
  `[poller] seriesAtRung DeatoN4U Error: nansen chart 403`, `series cut ngan hon cua so xin, keep previous
  AJjATm3L n=0`; LF additionally costs a second `label='exchange'` call (`exchangeLf`, `poller.ts:176`).

`fresh` is present because it comes from a single cheap gini-stats card (`updateTokenMetrics(..., 'gini')`);
`t100`/`lf` need the deploy-clamped hourly-stats series plus the exchange series, aggregated only inside the
12 h pass. Options: run one off-cycle pass now (queue is only 12 CAs), lower `POLL_SETUP_MS`, or wait.
