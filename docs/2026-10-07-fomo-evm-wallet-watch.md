# FOMO EVM wallet watch - runbook (2026-10-07)

**Scope:** Instance B only. Add one generic `EVM` wallet address; the API stores one row per supported chain (`base`, `bsc`, `robinhood`) so the existing chain-aware watcher, trade ingester, and holdings poller can use it without changing the wallet address at each screen.

## Coverage contract

The FOMO-only daemon is configured with `--chains base,bsc,robinhood --feed hybrid --no-min-usd-gate` and posts to instance B (`127.0.0.1:8125`). It reads all three chain rows from `/api/wallets`, writes trades through `/api/wallet-watch/trades`, and keeps its cursor/heartbeat under `/opt/fomo-wallet-watch/data`. Its systemd unit is `fomo-evm-wallet-watch.service`; deploy/start it with `make fomo-evm-watch-deploy` after instance B is healthy. It uses `/opt/fomo-watch/fomo.env` for the existing service token. Instance A's `wallet-watch.service` is not changed. The hybrid unit change in this branch has not been deployed.

RPC configuration:

| Chain | Ordered RPC pool | Final fallback |
|---|---|---|
| Base | `BASE_RPC_URL`: active Alchemy key first, then previous keys | `https://mainnet.base.org` |
| BSC | `BSC_RPC_URL`: `https://bsc-rpc.publicnode.com`, active Alchemy key, previous keys | `https://bsc-rpc.publicnode.com` |
| Robinhood | `ROBINHOOD_RPC_URL`: `https://rpc.mainnet.chain.robinhood.com`, active Alchemy key, previous keys | `https://rpc.mainnet.chain.robinhood.com` |
| Ethereum | `ETH_RPC_URL` (optional) | `https://ethereum-rpc.publicnode.com` |

Each env value is a comma-separated ordered URL list in the root-only `/root/signal-scan-monitor/alchemy-rpc.env`, shared by the FOMO watcher and instance-B API (holdings reads). Both clients append their public endpoint as the final fallback. As of 2026-10-23 the previous Alchemy keys return monthly-capacity 429; the active key is free tier and its `eth_getLogs` range is limited to 10 blocks. BSC and Robinhood therefore prefer their public endpoint; Base keeps the active key first because its public endpoint rejects wide log ranges. Ethereum currently uses its public endpoint unless `ETH_RPC_URL` is set. Robinhood HTTP chain ID is 4663; Ethereum is 1. BSC public RPC rejects address-less topic-only `eth_getLogs`, which is why BSC HTTP log polling is disabled.

Apply/restart both readers with `make fomo-rpc-apply INSTANCE=b`; this recreates only instance-B API, checks its health, then deploys/restarts the FOMO watcher.

The classifier nets receipt ERC-20 `Transfer` logs per `(chain, wallet, tx, token)`, so split fills aggregate, intermediate wallet assets cancel, and token-to-token swaps emit their net endpoints. For unresolved wallet transactions it reads a call trace (`debug_traceTransaction`/`callTracer`, with `trace_transaction` fallback only when the method is explicitly unavailable). The trace supplements standard ERC-20 `transfer`/`transferFrom` calls and successful native-value call frames; failed frames are ignored. Existing receipt logs take precedence, and duplicate trace legs are removed. `decimals()` successes are cached; unavailable/invalid decimals fail the block without guessing 18.

The feed subscribes to wallet-filtered WSS `Transfer` logs plus `newHeads`; it does not stream unrelated block logs. Confirmed `eth_getLogs` reconciliation and a separate bounded full-block scanner cover missed notifications and top-level wallet transactions. The scanner handles at most four blocks per chain per turn by default, with an independent `last_tx_block` cursor. When `*_TRACE_INDEX_RPC_URL` is configured, bounded `trace_filter` queries discover nested calls; `*_TRACE_RPC_URL` selects the transaction-trace provider pool. RPC calls try each eligible provider at most once per call, cache unsupported methods, and cool down quota/permission/transport failures; HTTP `Retry-After` is honored. FOMO EVM applies a 0.5-second minimum between HTTP RPC request starts per endpoint (`EVM_RPC_MIN_INTERVAL_SECONDS`), serializing requests to the same endpoint. This caps this daemon at two starts/second per endpoint, not the Alchemy account-wide usage of other processes.
`--feed hybrid` uses available WSS endpoints (derived Base/BSC WSS or explicitly configured Robinhood WSS) and paced HTTP polling only for chains without WSS. A WSS disconnect triggers bounded HTTP reconciliation and exponential reconnect; handshake failures back off from 2 to 60 seconds instead of resetting the delay on every failed attempt. Provider cooldown and `Retry-After` are honored before reconnect; reconciliation remains bounded and cursor-safe.
Each EVM daemon persists its cursors, recent headers, pending log inbox, candidate queue, RPC response cache, and trade outbox in `evm_watch_journal.sqlite3` beside its state file. SQLite WAL with `synchronous=FULL` commits each log before its cursor advances, and each candidate before its full-block cursor advances. The API outbox retries transient failures with backoff and survives restart; the server's `(wallet, ca, chain, tx, side)` unique key makes reposts idempotent. No RPC credential URL is stored in the journal.
While WSS is connected, `newHeads` supplies confirmation height without block-number polling; confirmed log reconciliation runs every 60 seconds when caught up and more often while bounded backfill remains. The daemon stores a 256-block header window. A detected reorg rewinds pending inbox/candidates/outbox/cache and both scan cursors to a sampled common ancestor, then replays from there. If a reorg invalidates an already delivered trade, that chain is durably halted and requires operator review; it does not silently emit an automatic correction.
The default confirmation depth is 8 blocks. Provider cooldowns are shared between equivalent HTTP/WSS URLs, so a quota-limited credential is not immediately retried over its other transport. 

The 2026-10-12 public RPC probes found no usable trace endpoint: BSC and Robinhood public endpoints rejected `trace_transaction`, and Base public RPC returned HTTP 401 for `debug_traceTransaction`; the configured Alchemy resources were quota-limited in the prior audit. Trace decoding and cursor failure behavior are covered offline, not verified against a live trace provider. Without `*_TRACE_INDEX_RPC_URL`, a contract-wallet call that is only nested in another transaction and has no wallet-indexed `Transfer` log remains undiscoverable. Without a working `*_TRACE_RPC_URL`, unresolved candidate transactions fail closed and do not advance `last_tx_block`. Cold start remains at the finalized tip; the bounded scanner does not replay historical blocks before its initialized cursor.

## Wallet UI and import

On the FOMO Wallets screen, choose `EVM (Base · BSC · Robinhood)` and enter a `0x` plus 40-hex address. Add, edit, and delete operate on the three-chain group; edits share name/tags/source/clan and imports use `chain=evm`. Export writes one generic EVM row. Existing chain-specific EVM rows are additively backfilled to the other supported EVM chains on instance B startup; instance A does not run this migration.

For the imported wallet list, a non-empty emoji is prefixed to the display name and retained as an `emoji:` tag; `x_handle`, each `flags` value, and `status` are retained as `x:`, `flag:`, and `status:` tags. A non-empty `group` maps to `clan`. `status:EXCLUDE` remains visible in the wallet list but is excluded from the EVM watcher; other statuses are watched. This batch has no values for `funder_address`, `cluster_id`, trade metrics, or `notes`.

## FOMO by semantics

The `FOMO by` breakdown keeps social FOMO-watch-list users and native tracked wallets in separate lists. Native rows show the configured wallet name, balance USD, buy/sell counts, net inflow, and last activity. `Tracked in` counts both lists. FOMO-user holding percentage remains the FOMO-user metric; native wallet balance/holding follows the chain-specific native wallet poller and is not merged into FOMO-user statistics.

### Holding source, freshness, and completeness

- FOMO `Bal` is updated from event-triggered `/balances` snapshots through the local prod bridge (100-row page cap: a full page is treated as possibly truncated and does not close missing positions), not a scheduled FOMO-user or user×CA sweep. The polling watcher posts a BUY/SELL alert; alerts within five seconds coalesce. A successful balances request is limited to once per user per minute, with one trailing refresh only when another alert arrives during that cooldown. The swap alert carries no holding amount, so the user-level balances response updates holdings.
- `/swaps` is requested only when a new BUY alert has no `tradeUsd`; a fill is stored only when one swap uniquely matches the same user, CA, chain, timestamp bucket, and (when available) position trade ID. The host watcher itself polls swaps through the same bridge, so a trade that already carries the quote-leg USD does not need a second swaps request.
- Scheduled `walletSweep` continues to refresh native tracked-wallet balances, but does not query FOMO `/balances` or FOMO-user RPC holdings. There is no daily FOMO backstop; event-triggered `/balances` is the current source.
- Existing API balance snapshots remain readable only inside their existing 24-hour freshness window. After that, absent a new alert-driven positions update or a fresh event-scoped wallet measurement, the dashboard reports Bal as unknown rather than treating an old value or missing row as zero. Users with no new alerts are not silently refreshed; missed polls can therefore leave Bal unknown/stale until a later swap.
- For tracked CAs, `holdingPct` is `amount / chain-scoped totalSupply × 100`. Positions amounts remain usable when supply is unknown, but percentage and USD balance are unknown if required supply or token price is unavailable. Reverted wallet `balanceOf` calls and incomplete multi-wallet sums remain unknown, not zero.
- Native tracked-wallet balances remain a separate RPC-backed metric and retain their normal wallet polling cadence; FOMO alert-driven reads do not replace them.


## 2026-10-23 RPC/CU optimization and live-only cutover

- Instance B EVM cursors are pinned to the live reconciliation tip (`last_block`/`last_tx_block`); there is no historical replay.
- The new Alchemy key is first for all chains. Old keys currently return `Monthly capacity limit exceeded` (429). BSC and Robinhood also put their public endpoint first; Base keeps Alchemy first because its public endpoint rejects wide log ranges.
- BSC HTTP `eth_getLogs` is disabled with `EVM_LOGS_DISABLED_CHAINS=bsc`: Alchemy/public BSC reject address-less topic filters. BSC still uses WSS `Transfer` subscriptions and the bounded top-level full-block scanner. This deliberately does not discover nested calls or token transfers where the wallet is not the top-level sender/recipient unless a trace/log provider becomes available.
- Robinhood's full-block scanner is disabled with `EVM_TX_SCAN_DISABLED_CHAINS=robinhood`: its block rate exceeds the bounded four-block scan, so the scanner only produced a growing historical backlog. Robinhood relies on its public 500-block log feed; top-level native transactions without a wallet `Transfer` log are not covered.
- Robinhood's public endpoint accepts 500-block topic-only `eth_getLogs`; its configured `chunk_span` is 500. Free-tier Alchemy allows only 10 blocks per `eth_getLogs`, so Base remains at 10.
- `watchers/evm/rpc.py` emits `# rpc/60s` with per-chain/per-method/per-host attempt counts and a separate `err=` list. Batches are not used; Alchemy bills the sum of subcalls. Use this line to compute CU from the Alchemy method table, not from elapsed wall time.
- Non-2xx JSON-RPC bodies are parsed. A free-tier HTTP 400 range error now halves the chunk instead of being logged as a transport failure; `"specify an address"` is a permission failure and fails over rather than triggering an endless halving loop.
