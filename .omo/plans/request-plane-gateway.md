# request-plane-gateway - Work Plan

## TL;DR (For humans)

**What you'll get:** One shared service that every copy of the app and every watcher goes THROUGH to talk to outside data providers (Nansen, GMGN, DexScreener), so the two running copies stop hammering the same providers and share one paid-data budget fairly.

**Why this approach:** The two running copies today sit on separate networks and each makes its own outside calls, so nothing coordinates limits or spending. Centralizing gives one place that respects every provider's limit and counts the meter, and it reuses rate-limit + browser-door machinery that already exists instead of inventing a second one.

**What it will NOT do:** It will not move the live market streams (they stay with each app copy). It will not move blockchain node access. It will not store data, compute signals, or make trading decisions.

**Effort:** Large
**Risk:** High - it rewires the outbound path of both live copies and touches the money-metered Nansen data budget.
**Decisions to sanity-check:** (1) a separate login token per app copy so usage is attributed; (2) Nansen paid budget split 50/50 between the two copies; (3) only providers that tolerate caching are cached (GMGN is NOT, it demands a fresh id per call); (4) the gateway is its own deploy unit on a shared private network, with a loopback port for the host watchers.

## Scope
### Must have
- One gateway service = the single writer for every SHARED request/response upstream: Nansen credit API, Nansen free browser door, GMGN, DexScreener. It returns the RAW upstream payload (body + status + a fixed allowlist of headers).
- `server/src/ratelimit/` limiters and the `crawl.ts` DoorPool move behind the gateway and are the ONLY copy of those limits. The DoorPool's own budgets remain authoritative for the browser door; the redundant, never-wired `nansen-door` limiter is NOT double-counted (see todo 10).
- A short-TTL cache with single-flight dedupe for providers/endpoints that tolerate it AND have DETERMINISTIC params (Nansen `token-information`/`holders`, DexScreener tokens/pairs/search). GMGN is EXCLUDED from both cache and dedupe (it mandates a fresh `client_id` + timestamp per call). Time-windowed Nansen flows (params carry a moving `from`/`to`, e.g. `tgm/flows`) are EXCLUDED from dedupe because each call's window differs so keys would never collide - caching them would be both a false hit AND a false proof; the e2e dedupe proof therefore uses a deterministic NON-credit endpoint (see todo 22). For CREDIT-bearing Nansen endpoints the cache/single-flight KEY INCLUDES THE CALLER, so per-caller credit attribution stays exact; cross-caller sharing is for non-credit endpoints only.
- Server (a+b) providers and the Python watchers call the gateway instead of upstream; both keep their parsing, business logic and DBs.
- Deployment: a dedicated compose project joining ONE shared external bridge network that a and b also join (membership added to the repo `docker-compose.yml`, so both instances and local dev inherit it). The gateway also binds a LOOPBACK host port so the host systemd watchers can reach it.
- Per-caller bearer tokens (one per app copy) so Nansen credit use is attributable; the Nansen credit budget is split EQUALLY between caller `a` and caller `b`, env-configurable with a safe default, and over-half is a soft-deny for that caller only.
- TDD: failing tests first for the proxy contract, the limiter wiring, the selective cache/dedupe, and the budget split.
- Fail-open: if the gateway is unreachable, an instance logs a warning and SKIPS that sweep; it does not throw, does not crash-loop, and does not lose data (its own DB writes are unaffected because the gateway is read-only). The instance's own data simply goes STALE for that sweep (no new upstream rows) but is never corrupted; there is NO cross-process stale cache (the cache lives in the gateway only).

### Must NOT have (guardrails, anti-slop, scope boundaries)
- NO stream/WS proxying. Solana WS, EVM WS and the FOMO WSS stay in-process per instance (`watchers/fomo/feed.py:39`).
- NO RPC-over-HTTP in v1. `solana-rpc`/`evm-rpc` stay local (`providers/solana.ts:202`, `providers/evm.ts:270`, `watchers/evm/feed.py:24-29`).
- NO durable queue / no job store / no DB in the gateway - read-only passthrough + limiter retry only. The gateway MUST NOT import `server/src/db.ts` (nor `better-sqlite3`): the relocated DoorPool is extracted into a DB-free module (todo 10).
- NO business logic, NO signal computation, NO DB writes, NO frontend changes inside the gateway.
- NO second limiter implementation and NO double-governing of the browser door (DoorPool budgets OR the `nansen-door` limiter - not both).
- NO caching or dedupe of GMGN responses.
- Do NOT wire the dead surfaces: `nansen.ts:419` dexTrades, `nansen.ts:433` currentBalance, `nansen.ts:266` balanceExtremes, `crawl.ts:906` nansenSeries, `crawl.ts:923` balanceSeries, `detail.ts:53` buildTokenDetail.
- Do NOT restart or reconfigure unrelated services on instance a; a changes only by becoming a gateway client + joining the shared network.
- NO upstream API key, token, or `.env` value ever written into the repo, plan, logs, or evidence.
