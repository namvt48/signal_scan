# fomo-user-watch - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** Dash B (instance "fomo") gets a FOMO copy of the wallet feature you already use: a list of FOMO traders you watch (typed in on the Tokens/Wallets screen, or imported from a CSV), a background listener that follows FOMO's live trade stream and records only the trades made by the people on that list, and one new column on the signals table showing which watched traders hit each coin - their name, buy/sell counts, money in, and how long ago.

**Why this approach:** FOMO's live socket is one shared firehose of every large trade on the platform, so we open exactly one connection and match the watch list locally instead of opening a connection per trader. We reuse the existing wallet-watch machinery end to end (same auth token, same CSV import/export, same "Tracked by"-style column) so operators already know how it behaves, and everything is switched off unless the build is instance b.

**What it will NOT do:** It will not change the first dashboard in any way. It will not show a trader's small trades (FOMO's feed only publishes large ones), and it will not feed the signal score or tier - the new column is information only. It will not try to discover thousands of traders automatically.

**Effort:** Large
**Risk:** Medium - the FOMO feed publishes large trades only, so the column is inherently partial coverage; the socket field names must be confirmed against live traffic before the column semantics are final.
**Decisions to sanity-check:** store watched traders' trades only (no full firehose archive, no pruning job); the new column is display-only and does not move the score; the watch list is supplied by hand/CSV rather than auto-discovered.

## Scope
### Must have
1. `fomo_users` watch list end to end: SQLite table + CRUD + CSV import/export on the server; a frontend input surface mirroring the Wallets tab; matching methods on the shared `DataStore` interface and BOTH implementations (`restDataStore`, localStorage `dataStore`).
2. `watchers/fomo/` daemon: ONE WebSocket to `wss://api.fomoapi.io/ws/alerts`, reconnect with backoff, local match against `fomo_users` (by `userId` falling back to `handle`), dedupe, batched authenticated POST, persisted watermark + heartbeat.
3. `fomo_trades` table + `POST /api/fomo-watch/trades` on the service token, idempotent on the FOMO `eventId`, FK cascade from `fomo_users`.
4. Signal plumbing that mirrors the existing Tracked-by pipeline: `fomoUserStats(ca, chain, now)` + batched `fomoUserStatsByCa(now)`, a `FomoUserStat` type on both sides, and `TokenSignal.fomoUsers`.
5. Exactly ONE new column on the signals table (group header + inline rows + modal breakdown), gated by a NEW build-time flag `VITE_SHOW_FOMO` that instance b turns on and instance a / local dev leave unset.
6. Server tests, a Python self-check test, a runbook doc, and a captured evidence artifact per todo.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- ANY change to instance a: its build flags, its port/bind, its data dir, its behaviour, or its signal payload. Instance a must produce byte-identical `/api/signals` output before and after.
- Per-trader WebSocket connections (the API has no per-user stream), or any bulk call to `/v2/users/{handle}` (2500 credits per hit).
- Persisting FOMO alerts from traders who are NOT on the watch list, and any retention/prune job for a full firehose archive.
- A discovery/leaderboard walker that auto-grows the list toward ~2000 handles.
- Any change to scoring, tiers, gates, or `trackedInflow`/`trackedActivityAt` from FOMO data - the column is display-only.
- A separate FOMO page, tab, panel, or route; a new tunable config knob; or a new npm runtime dependency (the consumer is Python, matching every other watcher).
- Committing, logging, or documenting the FOMO API key anywhere in the repo.
