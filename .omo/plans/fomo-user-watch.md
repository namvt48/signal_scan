<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** Dash B (instance "fomo") gets a FOMO copy of the wallet feature you already use: a list of FOMO traders you watch (typed in on the Tokens/Wallets screen, or imported from a CSV), a background listener that follows FOMO's live trade stream and records only the trades made by the people on that list, and one new column on the signals table showing which watched traders hit each coin - their name, buy/sell counts, how much they bought, and how long ago.

**Why this approach:** FOMO's live socket is one shared firehose of every large trade on the platform, so we open exactly one connection and match the watch list locally instead of opening a connection per trader. We reuse the existing wallet-watch machinery end to end (same auth token, same CSV import/export, same "Tracked by"-style column) so operators already know how it behaves, and everything is switched off unless the build is instance b.

**What it will NOT do:** It will not change the first dashboard's behaviour in any way. It will not show a trader's small trades (FOMO's feed only publishes large ones), and it will not feed the signal score or tier - the new column is information only. It will not try to discover thousands of traders automatically. It will not show a "profit/loss" or "net money in" figure, because FOMO's own numbers cannot support one honestly (see the captured schema below).

**Effort:** Large
**Risk:** Medium - the FOMO feed publishes large trades only, so the column is inherently partial coverage. This is a property of FOMO's data, not a bug in our code (one live connection to the app feed never sees a small trade). The socket schema is NO LONGER a risk: it was captured and pinned below.
**Decisions to sanity-check:** store watched traders' trades only (no full firehose archive, no pruning job); the new column is display-only and does not move the score; the watch list is supplied by hand/CSV rather than auto-discovered; the money figure shows LARGE-BUY SIZE only, never a net inflow (measured, see below). **AMENDED 2026-09-29 (user):** (a) a watched trader's BUY now ENQUEUES its CA into `tracked_cas` so the normal poller picks it up (todo 12); (b) each FOMO user row also shows `sellPnlUsd` - the sum of realised PnL on SELL rows - as a SEPARATE, individually-labelled figure, never combined with `buyUsd` (todo 13); (c) tracking a FOMO user's % holding is explicitly OUT of scope (alerts carry no wallet address, no token amount, no price).

## Scope
### Captured FOMO alert schema (empirical ground truth - do not treat any field name below as speculative)

> Captured by connecting ONCE, KEYLESS (free tier: 0 credits, ~60s-delayed), to `wss://api.fomoapi.io/ws/alerts`.
> Raw evidence: `.omo/evidence/fomo-user-watch/task-0-alert-sample.jsonl` - 109 messages, 102 alerts, 68,562 bytes, 115s window. This capture already happened; todo 10 does NOT need to repeat it, it consumes it.

Envelope: every frame is JSON with a top-level `type` in {`welcome`, `alert`, `heartbeat`}; `welcome` and `heartbeat` carry no trade data and MUST be ignored. A bare string `ping`/`pong` also occurs - skip non-JSON frames rather than raising.

Alert discriminator is **`alertType` (NOT `type`)** - `type` is always the literal string `"alert"`. Measured: `buy` 36, `sell` 41, `perp` 12, `thesis` 13. `listing` (<1% per the docs) did not appear.

Identity: **`trader` is the handle** and is present on 102/102 - so plain handle matching WORKS, and the ~178 CSV rows with no `userId` are still matchable. `userId` present 102/102. `eventId` unique on 102/102 (the dedupe key, confirmed, no collisions).

Chain: `chain` observed {`solana` 35, `robinhood` 23, `ethereum` 15, `hyperliquid` 12, `bsc` 12, `base` 5}; matching `chainId` {1399811149, 4663, 1, 1337, 56, 8453}. Only `sol|base|bsc` exist in this repo's `Chain` union - the mapping/dropping rule is pinned in todo 6.

Token: `tokenAddress` present on 90/102 - the 12 nulls are EXACTLY the 12 `perp` rows (a perp has no token contract). `token` is the ticker symbol.

Money - MEASURED, and the two directions mean different things (this is why the plan forbids a net-inflow figure):
- `alertType=buy` -> `usdValue` present 36/36 and byte-equal to `positionValueUsd` = the POST-FILL POSITION SIZE (not a purchase amount).
- `alertType=sell` -> `usdValue` present 41/41 and byte-equal to `realizedPnlUsd` = SIGNED REALIZED PnL (not sale proceeds).
- `alertType=perp` -> no money field at all (0/12). `alertType=thesis` -> none (1/13).
- Therefore `usdValue` is NOT one comparable currency across directions. Summing `buy - sell` over it is a category error and is explicitly banned. The only single-meaning money figure available is the SUM OF BUY SIZES.

On-chain-confirmation subset: `txHash`, `execTs`, `execLagMs`, `tradeUsd` appear on 17/102 only (a matched on-chain fill). Observed `execLagMs` range -3000..54. So `txHash` is frequently absent - never require it.

Timing: `ts` is the publish time in epoch milliseconds. `replay: true` on 97/102 marks delayed-tier delivery (the keyless/60s-delayed tier); the column is best-effort-fresh, not tick-accurate.

Text: `text` is a pre-rendered human string, e.g. `"kangshifu bought $STOCKER ($3K size)"`. Do not parse it; it is for log lines only.

Load: 102 alerts in 115 seconds (~0.9/s) across 6 chains. One shared socket plus a local set-membership test is trivial load - no backpressure, sharding, or worker pool is needed.

Docs quote that UI copy MUST NOT contradict: the feed is large trades only - "do not compute market share, trade counts, or volume from it". The column tooltip and the runbook must repeat this caveat.

### Must have
1. `fomo_users` watch list end to end: SQLite table + CRUD + CSV import/export on the server; a frontend input surface mirroring the Wallets tab; matching methods on the shared `DataStore` interface and BOTH implementations (`restDataStore`, localStorage `dataStore`).
2. `watchers/fomo/` daemon: ONE WebSocket to `wss://api.fomoapi.io/ws/alerts`, reconnect with backoff (accepting the gap - never backfilling), local match against `fomo_users` by the alert's `trader` handle (with an exact `userId` match preferred when the watch row has one), dedupe on `eventId`, authenticated POST of the survivors, persisted watermark + heartbeat under FOMO-SPECIFIC filenames (never the shared wallet ones).
3. `fomo_trades` table + `POST /api/fomo-watch/trades` on the service token, idempotent on the FOMO `eventId`, FK cascade from `fomo_users`.
4. Signal plumbing that mirrors the existing Tracked-by pipeline: `fomoUserStats(ca, chain, now)` + batched `fomoUserStatsByCa(now)`, a `FomoUserStat` type on both sides, and `TokenSignal.fomoUsers`.
5. Exactly ONE new column on the signals table (group header + inline rows + modal breakdown), gated by a NEW build-time flag `VITE_SHOW_FOMO` that instance b turns on and instance a / local dev leave unset.
6. Server tests, a Python self-check test, a runbook doc, and a captured evidence artifact per todo.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- ANY change to instance a's BEHAVIOUR: its port/bind, its data dir, its scoring, or its existing signal content. Instance a's `/api/signals` may gain ONE additive, always-empty (`[]`) `fomoUsers` field because the server code is shared - that is the only permitted diff, and it must be empty on instance a (no FOMO watch list exists there) and must not alter any existing field, order, or value. This replaces the earlier "byte-identical response" wording, which was unsatisfiable once the shared `TokenSignal` mirror changes.
- A per-watched-user WebSocket (one socket per trader), even though the docs show `?trader=<handle>`, `?userId=`, and `{"action":"subscribe"}` exist - with hundreds of watched users that is hundreds of sockets; ONE shared socket plus a local match is the design. Also banned: any bulk call to `/v2/users/{handle}` (2500 credits per hit) and any use of `/v2/alerts` for automatic gap backfill (125 credits per call).
- Writing ANY FOMO alert into `wallet_trades`, `wallet_token_state`, or any wallet accessor, and never reusing `insertTrades`/`kickWalletRow` for FOMO data - FOMO trades live only in `fomo_trades`. (Metis flagged this as an implicit-only constraint; it is now explicit.) AMENDED 2026-09-29 (todo 12): a watched trader's BUY may call `insertTrackedCa` + `kickCAs` to enqueue the CA on the tracked-CA queue - that queue is NOT wallet state; `insertTrades`/`kickWalletRow`/`wallet_trades`/`wallet_token_state` remain forbidden for FOMO data.
- Persisting FOMO alerts from traders who are NOT on the watch list; a perp/thesis/listing alert ever creating a row; any retention/prune job for a full firehose archive.
- A discovery/leaderboard walker that auto-grows the list toward ~2000 handles, and the daemon ever LEARNING a new watch user from the firehose (the stream may only enrich the `user_id` of a row that already exists).
- Any change to scoring, tiers, gates, or `trackedInflow`/`trackedActivityAt` from FOMO data - the column is display-only. (Enqueuing a CA per todo 12 is NOT a scoring change: the CA is scored by the normal poller exactly like any other tracked CA; FOMO data itself never feeds the score.)
- A COMBINED money figure (net inflow / profit / "money in/out" / buy+sell summed). AMENDED 2026-09-29 (todo 13): each FOMO user row may show TWO SEPARATE, individually-labelled figures - `buyUsd` = Σ BUY `usd_value` (post-fill position size) and `sellPnlUsd` = Σ SELL `usd_value` (realised PnL, may be negative). They must NEVER be summed (different quantities).
- UI copy, a tooltip, or a doc line implying the column is COMPLETE or that its counts/volume are platform-wide - FOMO's own docs say "do not compute market share, trade counts, or volume from it". The caveat must appear in the column tooltip and the runbook.
- A separate FOMO page, tab, panel, or route; a new tunable config knob; or a new npm runtime dependency (the consumer is Python, matching every other watcher).
- Committing, logging, or documenting the FOMO API key anywhere in the repo, and shipping the key value in a query string that reaches a log line (mask it).
