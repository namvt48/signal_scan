## 4. What this proves (and what it does not)

PROVEN:
- `MODE=mock` is the real literal (config.ts:18) and the mock path is live end to end:
  seedIfEmpty() -> 8 wallets + 4 tracked CAs, MockProvider selected, REAL walletSweep ran.
- 13 rows were WRITTEN into `wallet_token_state` by `replaceWalletBalances` (7 of them for
  the 4 tracked mock CAs; the other 6 are MOCK_CA_POOL ca05/ca06, which the mock provider
  emits but which are NOT tracked, so assembleSignals ignores them).
- Both dashboard columns render NON-TRIVIALLY through assembleSignals() (the exact function
  behind `GET /api/signals`, api.ts:209-211):
  * `Tracked by`   = non-empty name arrays, e.g. ["CT04","CT05","CT08"]
  * `Holding %`    = non-zero, e.g. 1.7693278163298964
  All 4 tracked CAs that received a wallet row rendered both columns (4/4).
- Bonus parity check inside mock: mock tokenInfo sets market_cap = price × supply, so
  `Σbalance_usd/market_cap` (old) and `Σtoken_amount/supply` (new) agree EXACTLY here
  (diff_pct = 0 on all 4 CAs). This is the arithmetic identity the change relies on;
  the real-CA version is evidence file 05.

NOT PROVEN HERE (stated plainly, not smoothed over):
- This is mock data (deterministic pseudo-random). It proves the pipeline renders, not
  that the number matches pre-change production on real CAs — that is 05-holding-parity.txt.
- `balance_usd` is 0 for the 6 ca05/ca06 rows because those CAs have no `token_state` row
  (not tracked -> never swept) so `getTokenState(ca)?.price ?? 0` = 0. That is the documented
  informational behaviour (ingest.ts:174-192) and it does NOT affect the two columns, which
  read `token_amount` / `supply` — visible in the output: ca05/ca06 have token_amount > 0
  yet never appear as signals (they are not tracked).
